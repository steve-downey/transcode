Review of PR #131, the SG16 review response — 2026-10-30

This document records a review of pull request #131 (sg16-review-response, head f225333) against three things: the pull request on its own, the SG16 mailing-list thread on P4246R0 it answers, and the WHATWG Encoding Standard as checked out at whatwg/encoding commit be17ac5. It is a triage document, not a set of fixes. What became of each point is tracked in docs/plans/pr131-review-adoption.md.

Status terms:

  • Confirmed means the behavior was reproduced, or follows directly from the code, the spec text, or a CI log.
  • Decision means a contract must be chosen before there is one correct fix.
  • Verify means the evidence indicates a likely problem, or a claim, that still needs a focused experiment.

Verdict

The PR answers the thread well in substance. The names follow the Encoding Standard, the WHATWG views are now the generic views over whatwg::decoder and whatwg::encoder, the std::text_encoding::id bridge goes both ways, and the four wording defects Jonathan Wakely listed are fixed in the generated clauses. Two findings block a merge, one of them a CI failure. Two thread points are under-answered, and two benchmark claims the paper and README rest on need confirming and surfacing.

Blocking

clang-regex-ci-failure

Finding: Every clang CI job is red. Status: Confirmed.

Commit 5965c43 ("tighten loose regexes") rewrote the PASS_REGULAR_EXPRESSION of 17 negative compile tests to GCC's phrasing, required for the satisfaction of 'X<T>' ... [with T = ...]. Clang reports the same failure as 'T' does not satisfy 'X' and candidate template ignored: constraints not satisfied [with T = ...]. All twelve clang jobs (19 through 22, C++23 and C++26, Debug, Release and MaxSan) fail those 17 tests, and "Required CI" fails with them. GCC jobs pass. The regexes on main were compiler-neutral (satisf.*forward_range, legacy_byte_range), which is why the failure is new.

PASS_REGULAR_EXPRESSION takes a list and passes on any match, so the GCC regex can stay and a clang regex be appended. The patterns below were checked against the diagnostics in the clang 19 C++23 Debug job log (job 123669031415); each matches its own test's output and nothing else in it.

x-user-defined-encoder

Finding: The wording says the Encoding Standard defines no x-user-defined encoder; it does. Status: Confirmed.

encoding.bs has an "x-user-defined encoder" section: an ASCII code point is its own byte, U+F780 to U+F7FF map back to 0x80 to 0xFF, and anything else is an error. The Standard's own note under "Encoders and decoders" says that only the replacement and UTF-16BE/LE encodings have no encoder. The library has never implemented this encoder, and on main that was a comment. This PR writes the claim into the proposed wording and the README:

  • [transcode.whatwg.encode] Mandates: "It defines none for utf_16be, utf_16le, replacement or x_user_defined."
  • [transcode.whatwg.encoders] Remarks: "for which the Encoding Standard defines no encoder".
  • README.md, the paragraph after the encode example.

The encoder is about ten lines, is stateless, and every scalar value encodes to one byte or none, so whatwg::encoder<x_user_defined> can model single_byte_text_encoder and keep the random-access path. If it is left out on purpose, the wording has to say the library does not provide it, not that the Standard does not define it. This is the one place the PR contradicts the spec checkout.

Spec conformance

Everything else was checked against the encoding checkout and matches.

  • docs/whatwg/encodings.json and all index files are byte-identical to the spec repository. The two spec commits after the one the paper's bibliography pins (a985b62) are editorial: "run these steps" is dropped from algorithm openings, and the peek loop is reindexed. The pin is still accurate.
  • whatwg::get_encoding is "get an encoding": strip leading and trailing ASCII whitespace, ASCII case-insensitive match against the label table. The generated name_table holds the Standard's names, which is what makes to_text_encoding_id land on windows1252 rather than on an alias.
  • whatwg::bom_sniff is "BOM sniff": a non-consuming peek of up to three bytes, same table, same order. Requiring forward_range is how a range says "peek".
  • whatwg::decoder<replacement> matches the replacement decoder: one error for any non-empty input.
  • The ISO-2022-JP encoder's "escape back to ASCII, then the replacement" matches the Standard's handler, which restores the code point, emits 1B 28 42, and only then returns the error. Encoder-supplied replacement bytes are the right model for that.
  • No encoder for replacement and UTF-16BE/LE: per spec.
  • Decision, one sentence owed in [transcode.whatwg.decoders]. The Standard says byte order mark handling is "not part of the encodings themselves" but of the wrapper algorithms (decode, UTF-8 decode, and TextDecoder with ignoreBOM false). The clause calls whatwg::decoder<C> "the decoder ... the Encoding Standard defines" and then gives it decode_first, which strips the mark. The behavior is unchanged and is what the Web Platform Tests expect; the remark should say the object is the decoder plus the BOM step of the Standard's decode wrapper, or SG16 will quote the note back.
  • The error modes are replacement and report. The Standard's "html" encoder mode (&#NNNN;) is not offered. Pre-existing and reasonable, but the paper now carries Jan Schultke's "inherit that mess" quote, so the question will come.

Benchmarks: claims to confirm, and where readers find them

Two claims carry weight in the thread and are stated in the paper and README on numbers that predate this PR's benchmark changes. Both need re-running on the PR head, because count_elements now consumes its values and the gcc-release preset now really builds at -O3, so the published numbers and the new ones are not comparable.

bulk-helper-vs-ranges-to

Finding: A bulk WHATWG helper adds nothing over view | ranges::to. Status: Verify.

The paper says there is "no measurable difference in speed between a named decode_to and the equivalent view | ranges::to composition", and early benchmarks said the same. That is the answer to Freire's buffer point and half the answer to Schultke's "range in, code units out": the eager helper is a name, not a faster path, and an eager API with a caller-supplied buffer would be the same loop again. The claim is load-bearing and is asserted without a table. Measure whatwg::decode_to<C>(r) and whatwg::encode_to<C, string>(r) against r | whatwg::decode<C> | ranges::to<vector<char32_t>>() and r | whatwg::encode<C> | ranges::to<string>(), and decode_into and encode_into against ranges::copy into a pre-sized buffer, at -O3 with values consumed, on the existing corpora. Put the table in the README's performance section under its own heading and cite it from the paper's "Bulk Operations" paragraph, with the preset and commit it was taken at.

naive-iconv-comparison

Finding: Every path in the library beats naive iconv. Status: Verify.

"Naive iconv" means the code a search for "run iconv into a std::string" produces with no other constraints: iconv_open, a std::string sized to a guess, a loop of iconv() calls that grows the string and fixes up the output pointer on E2BIG, a final resize to the bytes written, and iconv_close. The paper's "Before: iconv" example in the comparison table is exactly that code.

The benchmark does not measure it. The Raw iconv() rows in the README come from raw_iconv_process in benchmark/iconv_benchmarks.bench.cpp, which converts through an already-open handle into a static 4 KB buffer that it overwrites on every call, never grows, never copies, and never produces a container; it counts bytes and discards them. That is a floor for iconv() itself, not the program a user would write, and it is the row the README's "~4x" claims are measured against. The comparison the paper makes in prose (the "Before" code against the WHATWG pipe) has no row.

Add the naive loop as a benchmark, as the paper's example is written: std::string sized to four times the input, doubled on E2BIG, trimmed at the end, with iconv_open and iconv_close inside the timed region, since the "Before" code opens a handle per call. Then re-run the iconv, whatwg and pluggable suites on the PR head, confirm that iconv_transcode_to, the streaming WHATWG pipe and view | ranges::to each beat it, and publish it so that it is found:

  • one table in the paper, next to the "Before" and "After" examples it contrasts, with naive iconv(), the iconv() floor, iconv_transcode_to, the streaming WHATWG pipe and std::codecvt on the same corpus, so a reader who opens the paper for the motivation sees the numbers beside the code they describe;
  • one sentence in the table's caption saying what "naive" is, so the comparison cannot be read as a straw man, and one saying that the iconv() floor row discards its output;
  • the preset, compiler and commit for every row, since the published numbers were taken with count_elements discarding its values and the preset at -O2.

If the naive loop turns out faster than iconv_transcode_to on some corpus, that is a finding about iconv_transcode_to's staging, and it should be reported rather than left out of the table.

What this says:

  1. The README's Raw iconv() row is not a floor. glibc's iconv() called in 4 KB output chunks is four times slower than one call with a buffer that fits. The README's "iconv_transcode_to 83 µs against raw iconv 334 µs" and the "~4x" that follows from it measure the chunking in the baseline, not the library. The row should be renamed to say what it is (iconv() in 4 KB chunks) or dropped from the comparison.
  2. Naive iconv and iconv_transcode_to are the same speed. Sized 4x they are within noise on every corpus, in both directions, and the naive loop wins on Genji in one pass. That is the expected result: both are one iconv_open, one or two iconv() calls into a buffer that fits, one trim. iconv_transcode_to's value is that it closes the handle and never writes the loop, not speed, and the paper should say exactly that. Sized 1x, the naive loop pays 10% to 30% for its doublings and is still well under the chunked baseline.
  3. iconv_transcode_view and iconv_transcode_into lose to the naive loop by 4x to 10x. The view stages through a 4 KB buffer and so repeats the chunking cost the raw row shows; into pays back_inserter per byte. Neither is the row to put next to the WHATWG pipe. The paper's "iconv adaptor" section should carry these numbers and recommend iconv_transcode_to for a whole buffer.
  4. The WHATWG pipe beats naive iconv where the table lookup wins and ties it elsewhere. EUC-JP to Shift-JIS, which goes through the reverse index, is 2.5x to 3x faster than glibc on the 30 KB corpus and level on Genji. Shift-JIS to UTF-8 is level on 30 KB and 1.3x faster on Genji. UTF-8 to UTF-32 is 2.5x faster, but that row counts scalar values and the iconv rows write 228 KB of UTF-32LE, so it is not a fair pair; the view | ranges::to form from the README's own table is the row to use there, and it is not in the utf suite.
  5. So the claim to make is narrower than "everything beats naive iconv": the WHATWG pipe is never slower than the naive loop on these corpora and is faster by up to 3x on the legacy-to-legacy conversions; iconv_transcode_to matches it; the streaming iconv adaptor does not, and its row needs to say so.

Not done here: a view | ranges::to row for UTF-8 to UTF-32 beside the iconv rows (bulk-helper-vs-ranges-to asks for the same measurement for a different reason), a second machine, and the Wikipedia corpora the download tool could not fetch through this container's proxy (ar, ru, zh, ko answered 429; en, ja, Gutenberg, Aozora and Wikisource worked once a User-Agent was set, which tools/download_benchmark_corpora.py does not send and should).

The benchmark README.md under docs/benchmarks/ should also say, once, that numbers from before this PR and after it are not comparable and why.

Code and documentation

  • Confirmed: README.md footnote 5 now reads "P2728 selects its whatwg::encoding from the character type", a search-and-replace over-reach; it should still say "codec".
  • Confirmed: old names remain in docs/benchmarks/README.md (the transcode<codec::shift_jis, codec::utf_8> example near line 365), docs/benchmarks/PLATFORM_NOTES.md (whatwg_decode<utf_8>) and docs/p2728-alignment.md (whatwg_error, transcode_error_kind). CLAUDE.md is known and listed in the follow-ups.
  • decode_result carries a whatwg::error while the concepts are presented as generic and not WHATWG's. The paper owns this ("the protocol adopts WHATWG's error model"); it is the next question after the namespace one.
  • The random-access decode and encode iterators compare by position only, while the forward iterators also compare codec state. Consistent with the single-byte codecs being stateless, which the single_byte_text_encoder remark requires.
  • The PR carries the design response together with metrics/fanout-runs.jsonl, the -O3 preset fix and the count_elements change. The last two change the benchmark baselines for everyone; the PR body says so, and the benchmark README should too.
