Stage 6 — runtime codec objects

runtime-codec-objects. Decided 2026-11-08.

Processing an SMTP or MIME message is a prime use case: each part declares its charset in the data, and the reader wants the part's text as char32_t. Today it cannot get that without writing a switch over every encoding. whatwg::transcode_string takes runtime encodings but always re-encodes to bytes, and the code-point helpers decode_to<C> and decode_into<C> take the encoding only as a template parameter. It is also a gap against P2728, where getting char32_t from UTF is the straightforward case: code points are the common currency of text conversion, and getting them should be as easy for an encoding named at run time as for one named at compile time.

The fix, in two layers:

  • whatwg::dynamic_decoder and whatwg::dynamic_encoder, codec objects that hold a whatwg::encoding chosen at run time and model text_decoder and text_encoder. They plug into what exists: bytes | decode(whatwg::dynamic_decoder{e}) is a lazy char32_t range, and decode_or_error, encode, transcode(from, to) and ranges::to work unchanged. A MIME body arrives as a range out of a base64 or quoted-printable decoder, and can be large, so the lazy form matters. Each call to decode_one dispatches on the encoding; callers opt into that cost, so the paper's argument against dispatching on every code point by default still stands.
  • Runtime overloads of the bulk helpers on top of them: decode_to(src, e), encode_to(src, e) and the _into forms, by whatwg::encoding and by label. transcode_string becomes a thin layer over the same objects, and its 40-case switch goes away.

A MIME reader, as a real example, is the first caller of both layers and is written before them, so the API is shaped by the program that needs it:

  • examples/mime_reader/, its own example target. Not a library facility, and nothing in it goes near a specification header.
  • A small parser-combinator kit, copied from specgen's parse/cursor.hpp and parse/parser.hpp (themselves adapted from compile-time-scheme to run at run time; same author, same license) and adjusted to read bytes, since a MIME message is bytes until a part's charset says otherwise.
  • A grammar written close to the RFCs' ABNF, covering what a reader needs and no more: RFC 5322 header fields with folding; RFC 2045 Content-Type with token and quoted-string parameters, and Content-Transfer-Encoding; RFC 2046 multipart bodies with nested boundaries, preamble and epilogue skipped; RFC 2047 encoded-words in unstructured headers such as Subject. RFC 2231 parameter continuations are out of scope.
  • Base64 and quoted-printable as lazy byte views, so a part's text is body | base64 | decode(whatwg::dynamic_decoder{*cs}). Encoded-words are short, so they use the eager decode_to(bytes, label).
  • The charset goes through whatwg::get_encoding, so us-ascii and iso-8859-1 mean windows-1252 as they do in a browser. An unknown charset is reported, not guessed.
  • A few messages under examples/mime_reader/messages/, chosen to exercise the runtime path: an ISO-2022-JP text part, a Shift_JIS attachment, a windows-1252 quoted-printable part, a UTF-8 base64 part, and a KOI8-R encoded-word subject. A ctest runs the reader over each and compares its UTF-8 output with an expected file.

What was built, and how the questions were settled:

  • whatwg::dynamic_decoder and whatwg::dynamic_encoder in whatwg/dynamic_codec.hpp, clause [transcode.whatwg.dynamic]. Each holds a std::variant over the per-encoding codecs, indexed by the enumerator's value.
  • An encoding with no encoder, decided 2026-11-08: there is no constructor from whatwg::encoding. whatwg::make_dynamic_encoder(e) returns optional<dynamic_encoder>, empty for utf_16be, utf_16le and replacement. A precondition was the first design, and was dropped: a program holding an encoding from its input would have had to call has_encoder first, a second check that is easy to forget and repeats work the construction does anyway. The eager encode_to returns nullopt and encode_into returns false in the same case, so every runtime entry point reports it in the call that would have used the encoder. The Standard's "get an output encoding", which maps those three to UTF-8 as a browser does for form submission, is not applied implicitly; it could be offered as an explicit function.
  • Refinements: both objects model the flushable refinement, and the decoder models bom_aware_text_decoder, forwarding decode_first to decode_one where the encoding strips no BOM. Neither models the single-byte refinements.
  • constexpr: both are usable in constant evaluation, with constify tests.
  • Argument order, decided 2026-11-08: every eager helper takes the source first, then the encodings or codecs in "from, to" order, then any output: transcode_string(src, from, to), decode_to(source, e), decode_into(source, codec, out). The codec-object bulk helpers took the codec first and were changed to match; nothing outside their own header called them, and they had no tests, which they now have.
  • The eager runtime overloads dispatch once, through detail::with_encoding, and then run the compile-time loop. transcode_string uses the same dispatch, so its two 40-case switches are gone.
  • The MIME reader in examples/mime_reader/ decodes part bodies lazily through dynamic_decoder and encoded-words through decode_to(bytes, label). Its seven messages match Python's email package.
  • The paper's runtime example and "Template Parameter vs Runtime Selection" now show both forms and what each costs.

Still open:

  • The paper's dispatch-cost figure (about 121 instructions per call) was measured against transcode_string's old switch. The fold-based dispatch may compile differently, so re-run the dispatch benchmark with Stage 5's measurements before the figure is published again.
  • The exposition-only members of dynamic_decoder and dynamic_encoder show a detail:: type in the synopsis, as whatwg::decoder's $state$ does.

Not actionable

  • decode_result carries a whatwg::error while the concepts are presented as generic. The paper owns this; it is the next design question, not a defect.
  • The random-access iterators compare by position only. Consistent with the single-byte codecs being stateless.
